# Database Design

Owner: platform team · Status: living document (Stage 2 complete) · Currency: BDT

This document explains how the PostgreSQL schema is organised, which invariants are
enforced by the database itself, and how schema changes are applied in this
environment. `prisma/schema.prisma` remains the authoritative definition; this file
explains the reasoning behind it.

## 1. Sources of truth and assembly

| Artifact | Role |
| --- | --- |
| `prisma/parts/01..04-*.prisma` | The schema is maintained in four topic files (identity/config, catalog/inventory, orders/payments, resellers/CMS/ops) so a single 3,000-line file can be reviewed in pieces. |
| `prisma/schema.prisma` | Generated by `npm run db:assemble` and verified by `npm run db:assemble:check`. Never edit it by hand. |
| `prisma/migrations/**` | Forward-only SQL migrations. Applied with `npm run db:deploy` (see §5). |
| `prisma/migrations/extra-constraints.sql` | Hand-written CHECK constraints that Prisma cannot express; appended by `scripts/schema-tool.mjs`. |
| `scripts/fk-check.mjs` | Verifies that every foreign key in the database matches the `onDelete` action declared in the schema. |

## 2. Domain layout

The 111 models are grouped exactly like the business:

| Group | Models (examples) | Notes |
| --- | --- | --- |
| Identity & access | `Business`, `User`, `Role`, `Permission`, `UserRole`, `RolePermission`, `Session`, `PasswordResetToken`, `SecurityEvent` | One business per deployment. Permissions are data, roles are permission bundles. |
| Configuration | `BusinessSetting`, `Storefront`, `StorefrontDomain`, `StorefrontSetting`, `DeliveryZone`, `District`, `CheckoutFieldConfig`, `NumberSequence` | Settings are key/value rows typed by `lib/settings.ts`; document numbers come from `NumberSequence` under a row lock. |
| Catalog | `Product`, `Variant`, `ProductCategory`, `Category`, `Attribute`, `AttributeValue`, `VariantAttributeValue`, `ProductImage` | A product is a marketing shell; a variant is the sellable unit and the only thing inventory, pricing and orders reference. |
| Pricing | `PriceList`, `PriceListItem` | Prices are per list (default, storefront, reseller, wholesale) with quantity tiers and validity windows. |
| Inventory | `InventoryLocation`, `InventoryBalance`, `InventoryMovement`, `StockReservation`, `ReservationAllocation`, `StockAdjustment`, `StockAdjustmentReason`, `PreorderCommitment`, `PreorderAllocation` | Movement ledger plus per-location counters (§3). |
| Purchasing | `Supplier`, `PurchaseOrder`, `PurchaseOrderItem`, `GoodsReceipt`, `GoodsReceiptItem`, `PurchaseExpense`, `SupplierPayment` | Receipts are the only way stock enters through purchasing. |
| Sales | `Order`, `OrderItem`, `OrderAddress`, `OrderAdjustment`, `OrderStatusHistory`, `StockReservation` | Orders snapshot prices, costs and addresses; nothing is recomputed later. |
| Payments | `Payment`, `PaymentAttempt`, `PaymentEvent`, `Refund`, `PaymentReconciliation`, `CodCollection` | Provider events are keyed by `(providerName, providerEventId)` for idempotency. |
| Fulfilment | `Shipment`, `ShipmentEvent`, `CourierProvider`, `CourierWebhookEvent`, `CourierSettlement`, `CourierSettlementEntry` | Provider adapters keep their own credential rows; settlement entries link courier money to orders. |
| Exchanges | `ExchangeRequest`, `ExchangeItem`, `ExchangeReason` | Difference in paisa is positive when the customer owes money. |
| Resellers | `Reseller`, `ResellerOrderEarning`, `ResellerLedgerEntry`, `ResellerPayout`, `ResellerPayoutEntry`, `ResellerCollectionChange` | Earnings become payable only after COD settlement reconciliation. |
| CMS & media | `Page`, `PageBlock`, `Menu`, `MenuItem`, `MediaFolder`, `MediaAsset`, `MediaUsage`, `Banner` | Media assets are stored keyed by `objectKey` in S3-compatible storage. |
| Reviews | `Review`, `ReviewReport`, `ReviewVote` | One review per `(productId, customerId)`. |
| Integrations & ops | `ApiKey`, `Integration`, `WebhookSubscription`, `Plugin`, `BackgroundJob`, `OutboxEvent`, `Notification`, `NotificationRecipient`, `AuditLog`, `RateLimitBucket`, `IdempotencyRecord`, `MarketingIntegration`, `MarketingEvent` | Outbox + jobs drive side effects (webhooks, email) outside the request transaction. |

## 3. The inventory ledger

Inventory is the part of the schema where a bug costs real money, so it is designed
around three rules.

1. **Counters are derived, never written directly.** `InventoryBalance` holds
   `onHand`, `reserved`, `damaged`, `inspection`, `preorderCommitted`,
   `incomingQuantity` and `averageCostPaisa` per `(locationId, variantId)`. Only
   `applyStockMovement()` in `src/modules/inventory/service.ts` writes them.
2. **Every change writes an immutable movement.** `InventoryMovement` records the
   deltas, the counters *after* the change, the unit cost, the source document and
   the actor. Screens (stock history, audit) read the ledger, not the counters.
3. **Concurrency is handled by locking, not hope.** `applyStockMovement()` takes
   `SELECT … FOR UPDATE` on the balance row (creating it with `INSERT … ON CONFLICT`
   when absent), so two simultaneous receipts serialise instead of losing an update.

Additional guarantees:

- `InventoryMovement.idempotencyKey` is unique: replaying a receipt or webhook with
  the same key returns the original movement without touching stock again.
- CHECK constraints (in `extra-constraints.sql`) reject negative counters and
  `reserved > available`, so even a code path that bypasses the service cannot
  corrupt the ledger.
- Sellable availability is always `onHand − reserved − damaged − inspection`.
  `preorderCommitted` and `incomingQuantity` are promises, not stock.
- Weighted average cost changes only when `onHand` increases with a unit cost; it is
  updated with integer arithmetic (`weightedAverageCostPaisa`) and never with floats.

## 4. Keys, uniqueness and soft deletion

- **Money** is `Int` paisa everywhere. No `Float`, no `Decimal` in application paths.
- **Quantities** are `Int`.
- **Business-scoped uniqueness** uses compound keys, for example
  `Business.slug`, `Category (businessId, slug)`, `Variant (productId, optionKey)`.
- **Soft deletion**: `Product.deletedAt` and `Category.deletedAt` mark archived rows.
  Partial unique indexes (`Product_business_slug_live_key`,
  `Category_business_slug_live_key`, both `WHERE "deletedAt" IS NULL`) keep live slugs
  unique while allowing a slug to be reused after archiving. Because
  PostgreSQL still counts the soft-deleted row in a plain `@@unique`, slug generation
  in the service checks *without* the `deletedAt` filter.
- **One default per business** is enforced by partial unique indexes on
  `PriceList (businessId) WHERE isDefault` and
  `InventoryLocation (businessId) WHERE isDefault`.
- **Provider idempotency** keys: `PaymentEvent (providerName, providerEventId)`,
  `CourierWebhookEvent (providerCode, providerEventId)`,
  `CourierSettlement (businessId, providerCode, reference)`, `Order.idempotencyKey`,
  `GoodsReceipt.idempotencyKey`, `OutboxEvent.dedupeKey`, `BackgroundJob.idempotencyKey`.
- **Replay-safe side effects**: `StockReservation.orderItemId`,
  `PreorderCommitment.orderItemId`, `ResellerOrderEarning.orderItemId`,
  `ResellerPayoutEntry.ledgerEntryId`, `Review (productId, customerId)` and
  `ApiKey.keyPrefix` are unique so a retried request cannot duplicate financial rows.

## 5. Migrations in this environment

The Prisma schema engine cannot be downloaded here (`binaries.prisma.sh` is blocked),
so migrations are authored as SQL and applied by a small runner:

```bash
npm run db:migrate -- --name <migration_name>   # create the folder/SQL skeleton
npm run db:deploy                                # apply pending migrations, record sha256
npm run db:status                                # list applied/pending
npm run db:check                                 # assembled schema matches parts
npm run db:check-fk                              # foreign keys match the schema
```

`scripts/migrate.mjs` writes a `_prisma_migrations`-compatible table so the history is
portable to a normal Prisma workflow later. Rules:

1. Never edit an applied migration; add a new one.
2. No destructive resets. Data-preserving `ALTER TABLE` only.
3. After every migration run `npm run db:check` **and** `npm run db:check-fk`.
4. Generated clients must be regenerated (`npm run db:generate`) and must report 111
   model files in `src/generated/prisma/models`.

### Known drift found and fixed

The initial migration (`20260918000000_init_platform_schema`) was authored by hand and
created **every** foreign key with `ON DELETE SET NULL`. That contradicted the schema
(`Cascade`/`Restrict`) and made legitimate parent deletes fail on NOT NULL columns
(for example deleting a business while it still had a `Variant.productId` reference).
`scripts/fk-check.mjs` now compares all 209 constraints against the schema and
`20260919000100_fk_referential_actions` restores the declared behaviour
(127 `CASCADE`, 21 `RESTRICT`, plus `SET NULL`/`NO ACTION` where declared).

## 6. Testing the schema

Integration tests run against the real database (`tests/integration/*`). They create a
throwaway business per suite, exercise the service layer and tear the rows down in
dependency order. Before running the suite the database must be migrated and seeded:

```bash
npm run db:start && npm run db:deploy && npm run db:seed
npx vitest run tests/integration
```
